# Active-battle live validation gate

Status: ready to execute against a real authenticated HeroesWM battle.

This runbook validates the read-only closed loop described by `SPEC.md`:

`official battle client -> passive fetch/XHR capture -> extension bridge -> authenticated local daemon -> canonical BattleState revision -> planner -> revision/hash-bound recommendation -> human move -> new capture`.

It does **not** authorize autoclicking, gameplay commands, active polling of HeroesWM, or broad extraction of browser/runtime data.

## Prerequisites

1. Build and start `solver-daemon` on the default loopback endpoint `127.0.0.1:38471`.
2. Load the built MV3 extension from `extension/dist`.
3. Open the side panel and pair it using the six-digit code printed by the daemon.
4. Confirm the side panel reports `paired` and daemon health is `ok`.
5. Clear the `Live closed-loop trace` immediately before opening/entering the battle being used for validation.

## Minimal live smoke gate

Use one real authenticated PvE battle and observe at least one complete player-decision cycle.

Expected trace for an ordinary successful cycle:

1. `capture_forwarded` — MAIN-world fetch/XHR hook produced a whitelisted battle payload; trace contains metadata only (`battleId`, source, urlKind, sequenceHint, bodyBytes).
2. `capture_accepted` — daemon accepted the envelope. `revision` and `stateHash` identify the canonical publication visible at the end of that capture.
3. `plan_requested` — service worker scheduled replanning after the accepted capture.
4. `plan_result` — result is either:
   - `ok`, bound to the current state hash/revision; or
   - an explicit safe non-result such as `not_ready` / `stale` with a reason.
5. After the human performs the move, the next accepted battle update must publish a newer revision and trigger another planning cycle.

The side panel must never replace a newer recommendation with an older in-flight one. When a new state arrives during search, the expected behavior is a daemon `stale` result and/or an extension `plan_discarded_epoch` event; the old recommendation must not be rendered as current.

## Pass criteria for Browser Bridge smoke validation

The live bridge smoke gate passes only when all of the following are true:

- no gameplay request is generated by the extension/daemon; all HeroesWM observation remains passive;
- battle fetch/XHR traffic used by the game is not modified or delayed by the wrapper beyond cloning/async observation;
- pairing is required for all private daemon API calls;
- accepted captures produce monotonically increasing canonical revisions when observed state is republished;
- every rendered `ok` recommendation carries the same `state_hash` as current daemon status at render time;
- no stale result survives the revision/epoch/hash guards;
- unknown/partial protocol state produces explicit `not_ready`/diagnostic output rather than a fabricated recommendation;
- the trace is sufficient to identify the failing stage if any of the above breaks.

This smoke gate is **not** the final MVP/live benchmark. The formal invalid-recommendation and hard-PvE human-in-loop gates in `SPEC.md` remain separate and require a larger sample.

## When to activate the runtime-object fallback work

Do not implement a broad runtime scraper pre-emptively. Use the existing metadata-only runtime structure probe when the live trace shows one of these conditions:

- network payload is observed but cannot reconstruct a required current state field;
- client-visible legal actions are needed but cannot be derived from server payload/rules with the required recall;
- a battle mode uses a transport/state source not represented by the whitelisted battle responses.

For such a failure, preserve:

- the bounded live trace;
- daemon `/status` JSON;
- the metadata-only runtime structure probe result;
- the exact missing canonical field or legal-action fact.

Then implement the smallest explicit adapter for the proven runtime object/field. Do not read cookies, tokens, storage contents, credentials, unrelated globals, or execute arbitrary getters.

## Evidence to retain

For each manual live-validation session record:

- date/time and battle ID;
- extension/daemon commit SHA;
- whether the battle completed;
- number of accepted capture revisions;
- number of `ok`, `not_ready`, and `stale` planner results;
- any decoder warnings / semantic safety tier;
- any trace discontinuity and the first stage where it appears.

Do not put pairing bearer tokens, cookies, credentials, or full authenticated page/network dumps into the report.
