# Active-battle live validation gate

Status: ready to execute against a real authenticated HeroesWM battle.

This runbook validates the read-only closed loop described by `SPEC.md`:

`official battle client -> passive fetch/XHR capture -> extension bridge -> authenticated local daemon -> canonical BattleState -> planner -> canonical-state-bound recommendation -> human move -> new capture`.

It does **not** authorize autoclicking, gameplay commands, active polling of HeroesWM, or broad extraction of browser/runtime data.

## Prerequisites

1. Build and start `solver-daemon` on `127.0.0.1:38471`.
2. Load the built MV3 extension from `extension/dist`.
3. Pair the side panel using the six-digit code printed by the daemon and confirm daemon health is `ok`.
4. Clear the `Live closed-loop trace` immediately before the battle used for validation.

## Canonical identity rules

- Within one daemon process/session, accepted semantic publications have monotonically increasing `revision`.
- Numeric `revision` is **not** globally monotonic across daemon restarts. The extension scheduling identity is `(battle_id, revision, state_hash)`.
- Exact trimmed `t=<digits>` `battle.php` heartbeat/no-op frames are revision-neutral: they must not publish a new canonical state, cancel search, or trigger replanning.
- A transport/auth failure while requesting a recommendation may release only the scheduling claim for that same canonical key so reconnect can retry it. A late failure for an old key must never unlock a newer key.
- Semantic non-results such as `not_ready`, `finished`, and `stale` are not transport failures and must not create a retry storm.

## Minimal live smoke gate

Use one real authenticated PvE battle and observe at least one complete player-decision cycle.

Expected trace:

1. `capture_forwarded` — MAIN-world fetch/XHR hook produced a whitelisted battle payload; trace contains metadata only (`battleId`, source, urlKind, sequenceHint, bodyBytes).
2. `capture_accepted` — daemon accepted a semantic envelope. `battleId`, `revision`, and `stateHash` identify the canonical publication. A heartbeat may be observed but must leave revision/hash unchanged.
3. `plan_requested` — service worker schedules replanning for the current composite canonical key.
4. `plan_result` — either `ok` bound to current `battle_id/state_revision/state_hash`, or an explicit safe non-result such as `not_ready` / `stale` / `finished` with a reason.
5. After the human move, the next semantic battle update must publish a newer revision **within the same daemon session** and trigger another planning cycle.
6. If the daemon is deliberately restarted during a diagnostic retry check, a repeated numeric revision with a different battle/state hash must still be treated as a new canonical identity; a same-state transport failure must remain retryable after reconnect.

The side panel must never replace a newer recommendation with an older in-flight one. When state changes during search, expected behavior is daemon `stale` and/or extension `plan_discarded_epoch`; the old recommendation must not render as current.

## Pass criteria

The live bridge smoke passes only when all are true:

- no gameplay request is generated by extension/daemon; HeroesWM observation stays passive;
- official fetch/XHR traffic is not modified or delayed beyond cloning/async observation;
- pairing is required for private daemon API calls;
- exact `t=<digits>` heartbeat is revision-neutral;
- semantic captures advance revision monotonically within the same daemon session;
- scheduling/replanning identity uses `(battle_id, revision, state_hash)`, so restart revision collisions do not suppress a new canonical state;
- transport/auth recommendation failure is retry-safe for the same key and cannot unlock a newer key;
- every rendered `ok` recommendation matches current daemon `battle_id` and `state_hash` at render time;
- no stale result survives revision/epoch/hash guards;
- unknown/partial protocol state yields explicit `not_ready`/diagnostic output rather than a fabricated recommendation;
- the metadata trace identifies the first failing stage without storing secrets or full authenticated payloads.

The deterministic HTTP fixture and hosted CI prove the local safety contracts, but they do **not** replace this real-browser smoke. This smoke also does not replace the larger invalid-recommendation and hard-PvE human-in-loop acceptance gates in `SPEC.md`.

## Runtime-object fallback rule

Do not implement a broad runtime scraper pre-emptively. Use the existing metadata-only runtime structure probe only when the live trace proves a required canonical field/legal-action fact cannot be obtained from whitelisted network payload/rules. Then implement the smallest explicit adapter for the proven `stage.pole.obj` / `nowturn` field. Never read cookies, tokens, storage contents, credentials, unrelated globals, arbitrary getters, or render-space `scr_x/scr_y` as canonical grid coordinates.

## Evidence to retain

For each manual session record: date/time and battle ID; extension/daemon functional SHA; whether the battle completed; accepted semantic revision count; heartbeat count if useful; `ok`/`not_ready`/`stale`/`finished` counts; decoder warnings/semantic tier; any reconnect/restart used; and first trace discontinuity if one occurs.

Do not store pairing bearer tokens, cookies, credentials, full authenticated page/network dumps, chat, or unrelated user-facing battle metadata.
